# 业务逻辑反思

## 1. 业务核心不是“写一章”，而是“维护故事系统”

如果只把产品做成章节生成器，会很快遇到以下问题：

1. 人物行为不一致
2. 前后设定冲突
3. 支线失控
4. 章节推进失衡
5. 资料引用失真

因此核心对象不是单个章节，而是“可持续维护的故事状态机”。

## 2. 生成前必须先规划

必须要求 AI 按以下顺序执行：

1. 明确目标
2. 检索已有上下文
3. 提取约束
4. 制定计划
5. 分步执行
6. 复核一致性
7. 更新记忆

这也是必须引入 ReAct + Plan-and-Execute + Extraction 的原因。

## 3. 图谱不是装饰，而是控制一致性的关键结构

Neo4j 的价值不在“可视化”，而在：

1. 帮助 AI 查询人物冲突链路
2. 分析人物关系演化
3. 校验剧情节点影响范围
4. 支撑后续自动一致性检查

## 4. 章节生成应依赖多个前置资产

章节不是直接从一句提示词生成，而应依赖：

1. 项目规则
2. 世界观设定
3. 角色卡
4. 当前主线/支线节点
5. 章节目标
6. 上下章摘要
7. 风格要求

## 5. 需要明确 AI 的失败出口

AI 系统必须允许：

1. 任务失败记录
2. 中途人工接管
3. 回滚章节版本
4. 标记不可信资料
5. 重新规划任务

## 6. 轻量级架构的真实边界

React + FastAPI 是合理选择，但前提是：

1. 后端负责大部分编排逻辑
2. 前端不要过度状态机化
3. 异步任务与日志流需要设计清楚
4. Neo4j 接入保持边界清晰

## 7. 先做对，再做全

MVP 不应该一开始就做：

1. 多模型自动路由
2. 复杂多人协作
3. 全自动长篇完稿

MVP 应先做到：

1. 有结构化项目数据
2. 能创建角色与剧情
3. 能基于规则生成章节
4. 能记录 AI 计划、执行与问题
