# 解决方案记录

## 2026-05-31

### 方案 1: 文档先行的项目初始化

在项目为空目录的情况下，先建立架构文档和执行方案，而不是直接写散乱代码。

### 原因

该项目属于高约束、多模块、需长期接续执行的 AI 工程，没有先验文档会导致后续 AI 偏航。

### 方案 2: 先占位图谱接口，再逐步接入 Neo4j

先在后端暴露图谱路由和客户端封装占位，避免后续 API 结构反复变化。

### 原因

图谱能力是项目核心约束层之一，应尽早固定接口边界，但无需在第一轮就实现全部查询和同步逻辑。

### 方案 3: 先把任务流拆成项目/章节/模块三级边界

在实现真正的 AI 编排器之前，先把任务流数据结构细分到项目、章节、模块和步骤层。

### 原因

如果任务流没有在数据层做隔离，后续很难支持多小说并行、章节级追踪和 ReAct 步骤回放。

### 方案 4: Neo4j 不可用时自动回退到 SQLite 图谱

图谱接口优先从 Neo4j 读取，如果本地 Neo4j 未启动或查询失败，则回退到关系表生成图谱响应。

### 原因

该项目在开发期不能把图谱展示完全绑定到 Neo4j 服务状态，否则前端开发和任务流联调会频繁阻塞。

### 方案 5: 先完成基础设施容器编排，再继续业务深化

在继续扩展 AI 工作流之前，先补上 PostgreSQL、Neo4j、Redis、前后端容器化组合。

### 原因

如果没有稳定的运行底座，后续把任务执行器、联网抓取器和长期数据持久层接进来时会产生大量环境噪音和重复返工。

### 方案 6: 任务流采用“数据库历史 + Redis 运行态”双层结构

任务实体、步骤、日志继续保存在关系库中；任务当前状态、当前步骤、即时消息保存在 Redis。

### 原因

AI 工作流同时需要可追溯历史和可快速刷新的运行态，单用数据库或单用 Redis 都不合适。

### 方案 7: 任务步骤也采用 Redis 运行态

不仅任务本身要有运行态，任务步骤也要单独存入 Redis。

### 原因

ReAct 工作流的核心可观察对象不是“任务整体”，而是每个步骤的状态切换、当前阶段和失败点。

### 方案 8: 先实现最小 ReAct 执行链，再接入真实 AI 能力

先用后端服务把任务、步骤、运行态和步骤状态流转打通，再逐步替换为真实联网与模型调用。

### 原因

如果没有先打通执行链，后续接入真实 AI 时很难定位问题到底出在状态机、存储、工具调用还是模型行为。

### 方案 9: 搜索工具只通过环境变量注入，绝不写死在代码或文档中

把 Firecrawl 和 Tavily 的密钥能力作为运行时配置接入，而不是把示例密钥直接写进项目。

### 原因

这既保护隐私，也避免后续密钥泄露、误提交和环境漂移问题。

### 方案 10: 先做轻量规则映射，再升级为深层抽取

热点探索结果先通过可解释的规则映射到剧情线、角色候选和世界观条目，再逐步替换成更强的模型抽取。

### 原因

这样可以先打通“搜索 -> 创作资产”的主链路，同时保留后续升级空间，不会因为追求一步到位而卡住整体进度。

### 方案 11: OpenRouter 作为统一模型网关，运行时动态选择免费模型

不在项目里绑定固定模型，而是在运行时从 OpenRouter 免费模型池中发现并选择适合的模型。

### 原因

免费模型池是动态变化的，固定写死模型会很快失效；统一网关还能减少未来切换模型提供方的成本。

### 方案 12: 先做章节设计，再做章节草稿

在章节工作流中，先生成结构化设计稿和 beat sheet，再用它驱动正文生成。

### 原因

如果直接从资产生成正文，章节更容易漂移；先有设计层，后续修订、一致性检查和版本管理也更容易落地。

### 方案 13: 章节能力优先任务化，再扩修订链

先让章节设计和章节生成进入任务/步骤/运行态体系，再去补修订和一致性检查。

### 原因

没有任务化，后续章节修订链和校验链会缺乏稳定的执行上下文与观察点。
